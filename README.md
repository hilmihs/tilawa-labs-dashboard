# Tilawa Labs Dashboard — operations dashboard (public demo build)

An internal operations dashboard for a multi-programme Qur'an recitation education
provider. It aggregates data from upstream systems it does not own — a third-party
programme CMS plus several sibling in-house apps — and turns that into the things
coordinators actually act on: participant attendance, teacher discipline and
meeting coverage, monthly recaps teachers confirm over WhatsApp, warning-letter
PDFs, and a quarterly scorecard.

This repository is a **sanitised demo copy of a production app**, published so it
can be read. Production data, real names and phone numbers and the planning
`docs/` folder were removed; the organisation's identity is stripped throughout —
it appears only as "Tilawa Labs", every upstream hostname in the tree is a
placeholder (`tilawah.example.org`, `cms.example.com`, and so on), and the logos
and the letter signature are neutral placeholder images. The data you see in the
demo is synthetic, generated by `scripts/seed-demo.ts`. `DEMO.md` records exactly
what was changed, removed and sealed off.

## Architecture in short

Next.js 16 App Router (React 19, server components and server actions
throughout), Drizzle ORM over PostgreSQL, Tailwind 4. No separate API layer:
pages read the database directly in server components, mutations are server
actions in `actions.ts` next to the page, and the handful of real HTTP endpoints
under `app/api/` exist only for machine callers (cron, a bearer-token agent API,
file/PDF/xlsx downloads, an external sign-up site). Auth is an app-managed JWT
cookie (`jose`) with `coordinator` / `super_coordinator` roles; `middleware.ts`
redirects everything to `/login` except an explicit allowlist of routes whose
*credential is a signed token in the URL* — teacher magic links, recap
confirmation links, QR attendance cards, wall boards with no PII. Upstream
systems are reached by server-side clients in `lib/integrations/`, mirrored into
read-model tables by `lib/sync/`, and read back by the query/view-model modules
in `lib/`.

## Three decisions worth reading

### 1. The upstream systems lie about their own writes, so writes are verified by re-reading

Neither upstream is a documented API; both were reverse-engineered against the
real admin UI, and both return responses that do not describe what happened.
`API_MAP.md` is the field notebook: `DELETE /api/pertemuans/{id}` answers
`500 {"message":"Gagal menghapus pertemuan"}` while the row is genuinely gone
(24 deletes observed, 1 reported success, 23 reported 500, all deleted);
`POST /api/users/{id}` with `_method: PUT` answers `302 → /login`, as if the
session had expired, while the row genuinely changed. The partner reading system
does the same on `PUT /api/users/{id}`.

So the code does not treat an HTTP status as evidence. The clearest example is
`lib/hkm/nafi-accounts.ts` → `setNafiInternal()`: it reads the account first,
fires the `PUT` with `redirect: "manual"`, **ignores the response entirely — it
never inspects the status or body** — then re-fetches the account and decides
from the post-state alone:

```ts
const after = await getNafiAccount(userId);
const internal = after?.internal ?? before.internal;
return internal === (target === 1)
  ? { ok: true, internal, akun: after }
  : { ok: false, internal, akun: after, error: "… (nilai tidak berubah setelah dicek ulang)" };
```

The returned `internal` field is documented in the type as "the value afterwards
according to the re-fetch — the only truth here". Two related details in the same
file: the write payload echoes `name`/`email` straight back from the GET rather
than inventing them (sending `is_internal` alone is rejected 422), and the
comment block records that re-logging-in mid-run rotates the session so the write
silently lands as a guest.

Elsewhere the same distrust shows up as narrower rules:
`lib/sync/manage.ts` → `deletePertemuanFor()` accepts a failure only when it is
*not* the known lying message (`if (!r.ok && !/gagal menghapus/i.test(r.message))
return toResult(r)`); `lib/sync/push-meeting-taught.ts` is off unless
`TILAWAH_PUSH_TAUGHT=1` because there is no endpoint that sets a meeting's status
directly — it re-PUTs the whole meeting rebuilt from the stored `raw` and lets
the next sync confirm whether upstream kept it; and every write-back
(`lib/sync/push-late-status.ts`) fails soft, because the local row is already
saved and a failed push must never look to the user like their own submit failed.

### 2. Read models are separate tables from source-of-truth, refreshed on a schedule

`lib/db/schema.ts` is divided by ownership, and the section comments say so:

- *"Read-model tables refreshed by the sync engine — never written to manually;
  always overwritten by the next sync run."* These are the 12 `*_sync` tables:
  `halaqah_sync`, `students_sync`, `jadwal_sync`, `guru_sync`, `attendance_sync`,
  `guru_attendance_sync`, `hkm_users_sync`, `hkm_reading_history_sync`,
  `hkm_targets_sync`, `mabni_hafalan_sync`, `mabni_nilai_sync`, `maahir_sync`.
  They keep upstream's own ids as the join keys (`tilawah_halaqah_id`,
  `halaqah_user_id`, `tilawah_jadwal_id`) plus a `raw` jsonb column and a
  `synced_at` stamp, so a mirror row can always be traced back to what upstream
  actually said.
- *"Our own data (source of truth — nothing here comes from the upstream API)"*:
  `students` and guardians, `late_incidents`, `warning_letters`,
  `attendance_thresholds`, `teacher_meeting_confirmations`, `recap_attestations`,
  the scorecard tables, and the rest.

The practical payoff is that a sync can be destructive and re-runnable without
risking anything a human entered, and a page is never one failing third-party
request away from rendering nothing.

Scheduling lives in `app/api/cron/*/route.ts` (five routes: `sync-tilawah`,
`sync-hkm`, `sync-mabni`, `sync-maahir`, `refresh-scorecard`), each gated by
`Authorization: Bearer ${CRON_SECRET}`, with the loop itself in
`azure-pipelines-cron.yml`. The interesting part is what the route does *before*
calling upstream, all of it in `lib/sync/sync-window.ts` and
`lib/sync/absensi-fingerprint.ts`:

- A hard **blackout window** (05:00–08:00 WIB) that even the `?full=1` manual
  override cannot skip, because the upstream servers do their own morning batch
  work then. Hours are computed in `Asia/Jakarta` via `Intl.DateTimeFormat`, since
  the container runs UTC and every schedule in the product is WIB.
- A **fast/slow lane**: a programme with a meeting today keeps a 15-minute
  cadence during class hours; everything else drops to hourly — but never to
  never, because a schedule can change upstream and nothing local would notice.
  The "is there a meeting today" question is one indexed query against
  `jadwal_sync`, not an upstream call.
- **Overlap protection** (`isSyncRunning()`) so a 15-minute cron cannot stack runs.
- A **content fingerprint per halaqah** instead of trusting upstream's
  `updated_at`: writing an attendance row does not touch the parent halaqah row,
  and on one archive 45 of 99 halaqah had meetings updated after their halaqah
  row. The fingerprint hashes each enrolled student's attendance state *and the
  teacher of record*, because a teacher handover changes who a month's meetings
  belong to without touching a single attendance row — the comment names the
  incident where the mirror kept the old teacher and the recap billed the wrong
  person. Unknown on either side means "fetch it", so the failure mode is a
  wasted request rather than missing data.
- An incremental **high-water cursor** for the one upstream stream that has no
  date filter but does honour `sort_by=updated_at&sort=desc`
  (`lib/sync/presensi-bulk.ts` + the `tilawah_sync_cursor` table): page
  newest-first, stop at the first row older than the cursor, which replaces
  hundreds of per-halaqah detail calls with a few pages.

### 3. Business rules are pure functions, and the ones two screens share live in exactly one place

Anything a reader could disagree with is pulled out of the page into a tested
pure module. Two examples where the alternative was a screen that lies:

`lib/reports/meeting-fold.ts` is a single shared SQL CTE for one programme's
duplicate first meeting (one row named `Perkenalan`, one named `1`, both
order 1, one real meeting). Counting both inflates every teacher's expected
meeting count and leaves a permanent phantom gap. Its docstring states why it may
not be inlined: the monthly report (`lib/reports/queries.ts`) and the WhatsApp
recap (`lib/confirmations/recap.ts`) both depend on it, and if they folded
differently the same teacher would see two different meeting counts for the same
month — "and the teacher would rightly treat one of the two as a lie".

`app/[program]/disiplin/view-model.ts` is the teacher-discipline screen's payload
shaper. Its header documents three ways the screen would otherwise mislead: the
upstream route answers for every batch at once (so rows are filtered to the
coordinator's pinned batch), the scores still are not batch-scoped even after
that filter (so the view model surfaces `halaqahLuarBatch` instead of implying
otherwise), and "no data" is not zero (a teacher with nothing to score gets
`null` percentages and `null` rank rather than a rendered 0%). It also records
that its one derived flag was validated against upstream's own counter on a real
capture rather than invented locally.

That pattern is what the test suite covers — `vitest.config.ts` deliberately
includes `app/**/*.test.ts` so these page-adjacent `view-model.ts` files are
tested too, not just `lib/`.

## Running locally

Needs Node, pnpm and a local PostgreSQL.

```bash
pnpm install
cp .env.local.example .env.local      # set DATABASE_URL and AUTH_SECRET
pnpm db:migrate                       # applies drizzle/*.sql
npx tsx --env-file=.env.local scripts/seed-demo.ts
pnpm dev                              # http://localhost:3000
pnpm test                             # vitest
```

`scripts/seed-demo.ts` clears the 18 tables it owns and regenerates everything
from one fixed PRNG seed, so re-running it restores the same screens. Every
upstream hostname in `.env.local.example` is a placeholder, and every upstream
credential should be left **blank**: with them unset the integration clients and
the WhatsApp gateway cannot reach anything real. `DEMO.md` lists the full set of
variables that must stay absent (and why `ADMIN_SQL_ENABLED` must be the literal
string `"false"` — it fails open otherwise).

## Honest notes about this copy

- **One test file was deleted:** `lib/mabni/roster-xlsx.test.ts`. It read a real
  roster spreadsheet full of student and teacher names, and that fixture cannot
  be published. `lib/mabni/roster-xlsx.ts` itself is still here and still used by
  `lib/mabni/pengajar-koreksi.ts`; it is simply untested in this copy. The 110
  test files above are what remains.
- The letter PDFs used to embed a scanned handwritten signature of a named
  person. It is now a neutral placeholder (`assets/surat/ttd-signer.jpg`), as are
  the organisation logos — all replaced at identical pixel dimensions, because
  Next bakes a statically-imported image's intrinsic size into the layout.
- Upstream hostnames throughout the tree are placeholders
  (`tilawah.example.org`, `mabni.example.org`, `maahir.example.org`,
  `cms.example.com`, `dashboard.example.org`), and the organisation name appears
  only as "Tilawa Labs".
- Internal **programme slugs and codenames were deliberately left as they are** —
  `mabni`, `nurim`, `hkm` and friends are module paths, table names and route
  segments spread across the codebase, and renaming them would break things
  nothing would surface. Programme *display names* were replaced, so a reader
  will see an Indonesian codename in a path next to an English label on screen;
  that mismatch is intentional.
- The planning `docs/` folder and a session-less teacher-facing slide deck were
  removed; a handful of source comments still reference `docs/…` paths that are
  no longer in the tree.
- The repository also carries deployment config from production (Dockerfile,
  `deploy/` compose files, Azure and GitHub Actions pipelines). The demo itself
  runs on Vercel; those files are left in place because they are part of how the
  app was actually operated.
- Comments and some identifiers are in Indonesian — this was an internal tool for
  an Indonesian team, and I have not translated the code to make it look more
  portfolio-shaped.
